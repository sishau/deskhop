## 1. 需求与现场条件

**物理布局**（三屏相对关系固定）：

```
┌─────────────┬─────────────┐
│ 副显示器     │ 主显示器     │   ← 副显示器经 HDMI/DP KVM 盒（按钮切换）在两台电脑间切换
├─────────────┤             │
│ 笔记本内屏   │             │   ← 笔记本位于副显示器正下方
└─────────────┴─────────────┘
```

- 两台电脑均为 **Windows**（本机 = Output A；笔记本 = Output B）
- KVM 切换后拓扑变化：
  - **状态 1**（副显 → 本机）：本机 2 屏［副显｜主显］，笔记本 1 屏［内屏］
  - **状态 2**（副显 → 笔记本）：本机 1 屏［主显］，笔记本 2 屏［副显（上）／内屏（下）垂直堆叠］
- **核心诉求（v2）**：鼠标跨机切换**始终发生在副显示器边缘**
  - Profile 1：副显**下缘** ↓ 出界 → 笔记本；笔记本内屏**上缘** ↑ 出界 → 副显
  - Profile 2：副显**右缘** → 出界到达主机；主机主显**左缘** ← 出界 → 副显（笔记本主屏）
- KVM 由**盒子按钮**触发，固件无法感知 → 布局切换需要手动热键
- 硬约束：固件可执行区上限 **188 KB**（`misc/memory_map.ld`），且 `PICO_COPY_TO_RAM=1`，新增代码必须精简

## 2. 仓库现状调查结论（v0.80）

### 2.1 多屏模型

DeskHop 用**一维横向条带**描述所有屏幕（`src/mouse.c` 顶部图示）：

```
[B2 扩展屏][B1 主屏] ┃ [A1 主屏][A2 扩展屏][A3 扩展屏]
                     ↑ A/B 边界
```

- 每个输出（`output_t`）有 `pos`（扩展方向：A=Right、B=Left）、`screen_count`（1-3）、`screen_index`（当前屏，1 = 主屏）
- **主屏（index 1）必须紧贴 A/B 边界**；每块屏映射满 0~32767 虚拟坐标
- 切换判定**只看 X 轴**（`is_screen_switch_needed`）：跨板需超过 `jump_threshold`，本输出内部换屏无门槛
- 关键路径：`update_mouse_position` → `do_screen_switch`（`src/mouse.c:268`）→ `switch_to_another_pc`（跨板）/ `switch_virtual_desktop`（内部换屏）

### 2.2 Windows 绝对坐标限制（关键约束）

KB5003637 之后，Windows 把 HID 绝对坐标**钳制在"Windows 主显示器"范围内**。固件对策（`switch_virtual_desktop` 中 `state->relative_mouse = (new_index > 1)`）：

- `screen_index == 1` → 绝对坐标 → **只有 Windows 认定的主显示器可正常响应**
- `screen_index > 1` → 相对坐标（独立 HID 接口 `ITF_NUM_HID_REL_M`）→ 不受钳制

推论：**DeskHop 的 index-1 屏必须同时是 Windows 的"主显示器"**。

### 2.3 Windows 主显示器自动恢复（v2 已验证）

用户实测（笔记本侧）：副显设为笔记本主屏 → KVM 切走后内屏**自动**成为主屏 → 切回后副显**自动**恢复为主屏。Windows 按拓扑记忆主显示器设置，本机侧机制相同 → **笔记本无需任何手动配置**，本机仅需一次性设置（§5）。

### 2.4 已有能力（无需开发）

- web 配置页已支持每输出 Screen Count / OS / Position / Border / Park Position
- A↔B 的 Y 高度校准：`Right Shift + F12 + Y`（`screen_border_hotkey_handler`）
- 热键框架（`hotkeys[]`）+ UART 单字节同步包（`send_value`）——新增功能完全套用现有模式

### 2.5 缺口

1. 配置静态（存 flash），KVM 切换需要**运行时切换布局** → 热键 + UART 同步
2. 原生切换只看 X 轴，Profile 1 的 **垂直 A/B 边界是全新代码路径** → `mouse.c` 增加纵向分支

## 3. v2 目标设计 — "副显门户"两套 Profile

### 3.1 Profile 1 — 副显接本机（开机默认，`layout_profile = 0`）

| 条带槽位 | 物理屏幕 | 坐标模式 | 说明 |
|---|---|---|---|
| B1（主屏） | 笔记本内屏 | 绝对 | 副显切走后内屏自动成为笔记本主屏（已实测验证） |
| A1（主屏） | 副显示器 | 绝对 | **本机 Windows 主显示器须设为副显**（一次性，§5） |
| A2（扩展屏） | 主显示器 | 相对 | 本机内部，物理在 A1 右侧，原生横向切换 |

**A/B 边界为垂直方向**（A 在上、B 在下）——新增 Y 轴切换代码。

### 3.2 Profile 2 — 副显接笔记本（`layout_profile = 1`）

| 条带槽位 | 物理屏幕 | 坐标模式 | 说明 |
|---|---|---|---|
| B2（扩展屏） | 笔记本内屏 | 相对 | 物理在 B1 下方；相对模式由 Windows 管理真实 2D 位置 |
| B1（主屏） | 副显示器 | 绝对 | 笔记本 Windows 主屏 = 副显（用户已设，自动恢复已验证） |
| A1（主屏） | 主显示器 | 绝对 | 副显切走后本机只剩主显，自动成为 Windows 主显示器 |

**A/B 边界为水平方向** —— 与原生条带模型完全一致，跨板切换零新增代码。

### 3.3 边界行为总表（与用户描述逐条对应）

| Profile | 边界动作 | 类型 | 实现 |
|---|---|---|---|
| 1 | 副显(A1) 下缘 ↓ → 笔记本内屏(B1) | 跨机 | **新增**垂直切换 |
| 1 | 内屏(B1) 上缘 ↑ → 副显(A1) | 跨机 | **新增**垂直切换 |
| 1 | 副显(A1) 右缘 → 主显(A2)；主显 左缘 ← 回副显 | 本机内部 | 原生 |
| 1 | 副显左缘 ← / 内屏右缘 → | ~~跨机~~ | **屏蔽**（物理上不存在的边界） |
| 2 | 副显(B1) 右缘 → 主机主显(A1) | 跨机 | 原生 |
| 2 | 主机主显(A1) 左缘 ← → 副显(B1) | 跨机 | 原生 |
| 2 | 副显(B1) 下缘 ↓ → 内屏(B2) | 本机内部 | **新增**垂直换屏 |
| 2 | 内屏(B2) 上缘 ↑ → 副显(B1) | 本机内部 | **新增**垂直换屏 |
| 2 | 副显(B1) 左缘 ← / 内屏(B2) 右缘 → | ~~内部~~ | **屏蔽**（改走垂直，消除"悬空边"误触发） |

设计原则：**每条物理存在的边界都可切换，每条物理不存在的边界都屏蔽**。跨机切换始终以副显为门户。

### 3.4 设计要点

1. **切换 = 互换两输出的 screen_count**：Profile 1 = {A:2, B:1}，Profile 2 = {A:1, B:2}，同时两边 `screen_index` 复位 1、`relative_mouse` 复位 false。`pos`（A=Right/B=Left）两组 Profile 通用，**不需改**
2. **不落 flash**：`layout_profile` 存 `device_t`（RAM），重启回 Profile 1；KVM 状态与 Profile 一致性由用户热键保证
3. **两板同步**：执行板翻转 profile 后 `send_value(profile, LAYOUT_SELECT_MSG)` 广播，对板 `handle_layout_select_msg` 应用同样变换
4. 配置结构体不变 → `CURRENT_CONFIG_VERSION` 保持 8，**旧 flash 配置完全兼容**
5. 阈值复用：垂直跨板切换同样受 `jump_threshold` 约束（Profile 1）；Profile 2 垂直内部换屏无门槛（与原生内部换屏一致）

## 5. 一次性配置步骤（用户操作，非代码）

1. **web 配置**（`Left Ctrl + Right Shift + C + O` 进入配置模式）：
   - Output A：Screen Count = 2，OS = Windows，Position = Right（默认已是，= Profile 1）
   - Output B：Screen Count = 1，OS = Windows，Position = Left（默认已是）
   - Jump Threshold 建议 300~800（默认 0，同时约束水平与垂直跨板切换）
   - Speed X / Speed Y：建议 ≈ 32767÷屏宽(高)像素 —— X：2560px→13、1920→17；Y：1080→30、1440→23（默认 16/28 按 ~2048×1170 标定）。设为该值时绝对模式恰好 1:1 跟手，且相对扩展屏的内部回切触发点与物理边重合；Speed 偏大时顶墙折返会提前触发（提前量 = 屏宽 − 32767/Speed 像素）
2. **Windows 显示设置**：
   - 本机：副显接上时，把**副显设为"主显示器"**（唯一必需的手动设置）
   - 笔记本：**无需设置** —— 副显主屏身份已由 Windows 拓扑记忆自动管理（实测验证）
3. **Y 边界校准**（影响 Profile 2 的副显⇄主显 Y 映射与 park 位置）：光标分别在两屏等高处，按 `Right Shift + F12 + Y`

## 附录 A：剪贴板同步 — 二期预研结论存档

**硬性限制**：Pico 对电脑是纯 HID 设备，HID 协议读不到系统剪贴板 → **发送端必须有主机程序**把文本喂给 Pico；此为不可绕过的物理限制。

**已确认的决策**（2026-09-29 沟通）：双 Windows；经常需要传**中文** → 选定"剪贴板同步"路线（文本写入对端系统剪贴板，原生 Ctrl+V，完美支持 Unicode）；发送端临时脚本可接受；功能整体顺延至二期。

**拟定技术路线**：

1. 固件：normal 模式启用 vendor HID 接口（ITF 2 / EP 0x83；config 模式已验证该端点可用）；新增 `TEXT_*` UART 包（8 字节负载 = 1 字节序号 + 7 字节数据）双板互传；对端缓冲（建议 `TEXT_BUF_SIZE 4096`）
2. 主机端：发送脚本（PowerShell 或 Python+hidapi，读剪贴板 → SetReport 分块推送）；接收脚本（FETCH 请求 → Input Report 应答 → Win32 剪贴板 API 写入）
3. 接收端形态三选一：a) 两段式临时脚本（先收后发，零常驻）；b) 轻量常驻脚本（体验最好）；c) AutoHotkey 全局热键
4. 安全权衡：normal 模式开放 vendor 接口后，本机任意程序理论上可读对端缓冲/注入文本 —— 可选"武装热键"（如 `Right Ctrl + T`，60 秒窗口，UART 同步）收窄攻击面
5. 预估增量：固件 +3~4 KB flash / +4 KB RAM；不与一期冲突，可独立合入；体积同样受附录 B 预案保护

## 附录 B：固件体积裁剪预案（超限时按序执行）

**前提认知**：188 KB 上限**只针对可执行区**（`misc/memory_map.ld` 的 `__FLASH_LEN = 188k`）；disk image（64 KB）、fw metadata（4 KB）、flash config（4 KB）在别处，不占此额度。`PICO_COPY_TO_RAM=1` 影响 RAM 不影响 flash 占用。

**第 0 步 — 先测量再动手**：编译未修改的 v0.80 基线，记录 `.bin` 大小与链接器 `--print-memory-usage` 输出，确认实际余量。若余量 > 5 KB，一期 +2 KB 无需任何裁剪。

**第 1 步 — 编译选项（零功能损失）**：
- 检查当前优化级别：若为 `-O3`/`-Ofast` 改 `-Os`，典型节省 5~15%
- 确认 `-ffunction-sections -fdata-sections` + `-Wl,--gc-sections` 已启用（pico-sdk 通常默认启用，验证即可），剔除未引用函数

**第 2 步 — 编译期裁剪（按性价比排序，均为与本用例无关的功能）**：

| 优先 | 裁剪项 | 位置 | 预估节省 | 代价 |
|---|---|---|---|---|
| 1 | 屏保动画（pong/jitter + 3 个热键 + 任务） | `screensaver.c`、`handlers.c`、`main.c` 任务表 | 2~4 KB | 无屏保动画 |
| 2 | 鼠标加速度曲线（含 `sqrtf` 软件浮点） | `mouse.c` `calculate_mouse_acceleration_factor` | 1~2 KB | 恒定 1:1 速度（可用 speed_x/y 补偿） |
| 3 | macOS 切换 workaround | `mouse.c` `switch_virtual_desktop_macos` | ~0.5 KB | 双 Windows 用不到 |
| 4 | 数位板/digitizer workaround | `usb.c` `digitizer_active` 相关 | 0.5~1 KB | 无数位板支持 |
| 5 | 跨板 UART 固件升级 | `fw_upgrade.c` 及相关消息 | 2~4 KB | 失去"另一块板刷机"便利，改 USB BOOTSEL（**最后才裁**，属安全网） |

**第 3 步 — 兜底**：若仍不足，评估精简 TinyUSB 描述符/端点配置（风险高，需回归测试枚举兼容性，原则上不走到这一步）。

裁剪全部走**编译期条件编译**（`#if FEATURE_X`），不破坏上游代码结构，便于日后同步上游更新。

## 附录 C：免热键自适应探讨（2026-09-29 第二轮讨论）

**问题重述**：KVM 按钮切换只发生在视频路径；希望布局 Profile 与 active_output 无需热键、自动跟随屏幕变化。

### C.1 为什么纯固件自适应不可行（信号不存在）

- Pico 不在视频路径里：看不到 EDID、热插拔事件、显示拓扑。KVM 切换前后，Pico 可观测的世界（HID 输入流、USB 设备侧事件、UART、GPIO）**逐比特不变** —— 切换只改变"哪台电脑驱动副显"，而这个信息不经过任何 Pico 能读到的通道
- HID 对设备侧是单向的：固件发绝对坐标，拿不到 OS 光标实际落点 → 无法感知"坐标被 Windows 钳制"，也就无法反推主屏归属
- 行为启发（按出界方向推断副显归属）无法覆盖视频真相：一旦推断与 KVM 实际状态相反，用户立刻看到光标与输入落点失配（错误归属下绝对坐标被钳制，表现为"光标卡在屏边"）
- 结论：这不是实现难度问题，是信息论意义上的无信号。自动化的前提是**新增一条感知通道**

### C.2 路线 A（推荐）：主机端探针 + vendor HID

- 两台电脑各跑一个常驻小脚本（AutoHotkey ~20 行或 PowerShell + `SystemEvents.DisplaySettingsChanged`），监听 `WM_DISPLAYCHANGE`，把本机**屏幕数**（可选附主屏标识）经 vendor HID SetReport 推给各自的 Pico
- 固件侧：normal 模式启用 vendor ITF（ITF 2 / EP 0x83，**即二期剪贴板的既定前置**，+1.5~2 KB），新增 `DISPLAY_TOPOLOGY_MSG`（UART 双板同步），由 {A.count, B.count} **推导** profile（A=2 → 垂直门户；B=2 → 水平门户）；热键降级为手动兜底
- **active_output 自动翻转规则**："副显换主人 → 输入跟随副显的新主人"（KVM 切副显的语义就是换电脑）。用**成对事件**判定以保证确定性：A 丢屏 ∧ B 得屏（窗口内）→ 副显 host→laptop，切 Profile 2 + active→B；反之亦然 —— 副显单纯断电（host 丢屏但 B 无得屏）不会误触发
- 工程细节：双板去抖（双方报告齐或 1.5 s 超时才应用）；agent 启动时主动上报一次 → 顺带解决 R5"重启后 profile 固定"的残余场景；单 agent 掉线 → 保留最后有效 profile，热键兜底
- 代价与收益：两个常驻脚本（用户已在二期接受该形态）；vendor HID 与主机程序两块基础设施与二期剪贴板**一次投入两用**

### C.3 路线 B：KVM 切换事件的硬件直采

- **B1 按钮并联**：拆 KVM 盒，把切换按钮的信号线（通常为对地短接）并联一根线到 A 板空闲 GPIO（高阻输入 + 上拉 + 限流保护）。按下 = 精确切换事件 → 自动翻转 profile + active_output。零软件依赖、零延迟、100% 确定
- **B2 非接触**：光电三极管贴在 KVM 通道指示 LED 上 → GPIO。不拆盒，但怕环境光与对位偏移
- 前提：万用表确认按钮电气形态；注意走线距离（KVM 盒在桌面、Pico 在机箱后）

### C.4 v2.1（并入一期主方案的增量）：热键一键化

- 语义升级：`Right Ctrl + M` = "我刚按了 KVM"—— 翻转 profile 的同时 `set_active_output()` 到副显的新主人（Profile 1 → A，Profile 2 → B），光标按现有虚拟坐标比例落到副显上。**仅 +1 行**（toggle handler 内调用既有的 `set_active_output`，无需新增映射逻辑）
- 用户操作序列从"KVM 按钮 + 切输出热键 + 布局热键"退化为"KVM 按钮 + Right Ctrl + M"（约 1 秒）
- 原有 output 切换热键保留（应对"看副显但打字给主机"等少数场景）

### C.5 已否决的思路（备查）

- 出界方向推断副显归属：与视频真相冲突，见 C.1
- 键盘 LED output report 保留位走私 1 字节（免固件改动）：与 OS 的 LED 写入竞争、仅 1 字节、极脆弱
- Agent 经 SendInput 触发 config 模式热键再走既有 API：SendInput 合成键不经过 Pico 物理键盘，固件永远看不到

### C.6 建议节奏

1. **一期**（主方案 v2 + C.4 一键化）—— 纯固件，按 §4 清单实现
2. **1.5 期**（路线 A）—— 固件 +1.5~2 KB 与两个小脚本；与二期剪贴板合用基础设施，届时一并验收
3. **路线 B** —— 视动手意愿随时叠加；事件源与路线 A 互斥使用，热键始终为最终兜底

## 附录 D：隐藏坐标与"让 Windows 判断有效性"探讨（2026-09-29 第三轮）

**用户提案**：两块 Pico 各维护一份隐藏鼠标坐标（属实：输入板在 `update_mouse_position` 累计 `pointer_x/y`，输出板经 `handle_mouse_abs_uart_msg` 在远程输出激活时镜像，`protocol.c` 还将其暴露为只读 API）→ 能否让 Windows 判断坐标是否有效来移动鼠标，甚至不判断，"只有在有效桌面上鼠标才有可见移动"？关键问题：如何判断鼠标是否有效，从而把键盘事件路由到对应电脑。

### D.1 两个硬伤

1. **Windows 不做"有效/无效"判断**：每台电脑的 0~32767 映射它自己的整个虚拟桌面，任何坐标都"有效"——落在拓扑之外的实际行为是**钳制/落在别的屏**（KB5003637：绝对坐标钳到主显示器），不存在"坐标落空、光标不动"。且两机坐标空间互不对齐（各自按自己的拓扑比例映射），同一坐标发给两台 = **两个光标同时动** + 按键滚轮双份送达
2. **判断结果无法回流**：HID 对设备侧单向，"光标是否可见移动"发生在 OS/显示器侧，固件零反馈通道（LED output report 与光标无关）

### D.2 信息论封口（比 C.1 更强的表述）

物理手势图 **内屏 ↔ 副显 ↔ 主显**（含各边方向与邻接关系）在两种 KVM 状态下**完全相同**——变化的只是副显背后是哪台电脑。因此任意输入流（鼠标增量/按键/时序）在两种状态下都是自洽的解释：**"副显归属"这一比特不存在于任何固件可观测量中**。不加热键、不加探针、不加硬件，任何推断方案都无法恢复它。

### D.3 提案中可存活的内核：全相对模式（Scheme R，存档备查）

"让 Windows 自己管光标"推到底 = 两机全程相对模式：

- **消失的状态**：绝对/相对模式切换、"哪块屏是 Windows 主屏"的知识、边界校准（Right Shift+F12+Y）、Y 缩放（`scale_y_coordinate`）、逐屏坐标映射；**输出内部换屏完全交给 Windows**，固件只建模一条跨机共享边界
- **跨机落点**：切机后用一条绝对报告 warp 到对端主显示器的比例位置——无论拓扑怎么变都落在真实屏幕上（"有效桌面才有可见移动"在落点时刻成立，且天然跟随 KVM 自动切换的主屏）
- **代价**：
  1. 边界锚定退化——v2 的精确边缘来自"每屏满量程 0~32767 + 换屏复位指针"，几何无关且免费；全相对模式下共享边在物理鼠标计数空间中的位置未知（无 EDID，不知屏宽），要恢复精度就得重新建模内部屏边界 → 复杂度收敛回 v2
  2. 落点从"贴边精确"变为"主屏比例位置"
  3. 副显归属那 1 比特依然缺失（共享边是竖是横仍需 profile），**热键省不掉**
- **结论**：不是免费简化，而是"固件状态 ⇄ 边界精度"的权衡。若未来追求极致精简固件可重启此路线

### D.4 边界手势（推墙）——固件唯一能自造的"有效性"信号

- 固件**可以**观测：虚拟位置贴死在禁用边（钳制在 `move_and_keep_on_screen` 里可见）+ 用户持续单向推进（增量不断同向）→ 视为"模型与现实不符"信号 → 翻转 profile 并跟随副显新主人
- 价值：profile 错误时**手不离鼠**就地修复，比键盘热键自然
- 风险：快速甩动与刻意推墙的区分需调阈值（如累计推进量 + 时长双门槛）；仅部分位置有"墙"可推（cursor 不在禁用边附近时无信号）
- 定位：v2.x 可选增强，本质仍是手势确认而非自动检测，不改变"热键兜底"架构

### D.5 对"键盘跟随"问题的直接回答

- 现架构中键盘路由 = `active_output` = 固件虚拟位置的推论，**自洽、无需判断有效性**——固件是虚拟坐标空间的权威，OS 光标只是它的投影
- 若"有效"指"在真实存在的屏上"：固件不可观测、也不必要——OS 钳制保证光标永不丢失，最坏情况（profile 错误）表现为光标镜像到错误屏幕或卡边，**用户看得见、固件看不见**
- 缺失的 1 比特只有四个来源：热键（v2/v2.1）/ 主机探针（路线 A）/ GPIO 直采（路线 B）/ 边界手势（D.4）

### D.6 机制详解：为什么 v2 边界精确而全相对失锚（2026-09-29 追问）

**v2 的"免费技巧" = 三个互相咬合的设计**：
1. **满量程帧**：每块屏一个独立坐标系，长度恒为 0~32767 —— 坐标值即屏内比例位置，屏幕边界 = 坐标两极。全程不含任何几何量（屏宽 px、分辨率、排列、EDID 均不需要）
2. **入界复位**：每次换屏/换机，指针复位到"光标正经由的那条物理边"（`switch_virtual_desktop`：direction==RIGHT→MIN；`switch_to_another_pc`：direction==LEFT→MAX）→ 新帧原点与一条真实物理边重合
3. **绝对 = 投影**：主屏（index 1）上固件是位置权威，OS 光标是虚拟坐标按屏比例的投影 → "虚拟到极"与"光标到物理边"是**同一事件**，不是两件事恰好同步

- **条带不变量"主屏必贴 A/B 边界"⇒ 跨机判定永远发生在绝对屏上 ⇒ 最关键的边界零漂移**。扩展屏（相对模式）上的内部回切有条件精确：未顶墙时虚拟指针与 OS 光标锁定（同源增量、可逆），顶住远端非边界墙继续推进才吸收计数产生滞后，且一回到绝对主屏立即重锚定——漂移不累积、不污染跨机判定
- **Speed 因子的真实角色**（defaults.c：X=16/Y=28，[1-128]）：虚拟指针按 `move×speed` 累计而相对报告发原始增量（mouse.c:344-348），二者比例 = Speed 因子。X16/Y28 ≈ 按"横 2048 / 纵 1170 计数穿屏"标定，恰好匹配 16:9 屏的纵横比（16/28 × 16/9 ≈ 1.02）——它只决定扫屏快慢与相对模式的内部阈值精度，**不影响绝对模式的位置精度**；本质是手动供数的几何代理旋钮
- v2 全程唯一必须知道几何的地方（跨屏 Y 映射）由用户手动供数（Right Shift+F12+Y）——设计哲学：**不测量，要么定义（边界=极点）、要么问人（校准热键、Speed 因子）**

**Scheme R 的失锚**：
- 只有一条全局计数带，原点至多锚在"上次切换时刻"，且锚点物理位置（warp 到对端主屏比例点）本身不是边界
- 共享边在计数带上的刻度 = Σ(途径屏宽 px) × OS 灵敏度系数。两个不可知：无 EDID（Pico 不在视频路径，EDID 走 GPU↔显示器的线缆）；灵敏度/加速度设置在 OS 侧不可读。阈值两难：小了半路误切，大了要"穿墙"
- 顶墙空转（光标钉死、计数照走）吸收计数 → 锚点失联，误差 = 吸收量（无界）；OS"提高指针精确度"开启时快去慢回落点不同，连计数可逆性都破坏
- 补救 = 为每块屏重建"已知原点的帧" → 须检测内部边 → 须内部几何 → 须标定协议（且灵敏度一变就重标）→ = v2 的模型 + v2 不需要的标定负担。v2 的几何由 Windows 免费供给（绝对坐标归一化是 Windows 做的）——这就是"复杂度收敛回 v2（并超过）"的准确含义
